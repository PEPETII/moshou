# 玩法创新方案：跳出传统塔防框架

版本: 1.0
日期: 2026-09-16
类型: 设计提案（非工单，实施前需按 AGENTS.md 另行创建工单）

---

## 0. 结论速览

**核心判断**：当前的"文字内核"停留在**数值皮肤层**，而非**规则生成层**。融合系统（`js/config/fusion.js` 的 39 组配方 + 5 条进化链）本质上是"两个标签相加 = 一个更强的标签"，玩家可用的动词始终只有四个：**放置、升级、融合、等待**。因此无论叠加多少融合方式，体验都只是"数值组合的排列组合"，而非"文字本身在玩"。

**破局方向**：文字必须具备**生成规则的能力**，而不只是被规则描述的客体。汉字有五个可被规则化的维度，目前只用了不到一个：

| 维度 | 内容 | 当前利用度 |
|---|---|---|
| 字形 | 结构（左右/上下/包围/品字） | 未使用 |
| 字义 | 语义组合、六书 | 部分（融合名） |
| 字音 | 同音、多音、押韵 | 未使用 |
| 书写 | 笔画、笔顺、笔墨浓淡 | 仅作美术 |
| 文法 | 组词、句读、对仗 | 未使用 |

**推荐方案**：不做六选一，而是把**方案三（语法羁绊）+ 方案四（墨为血）+ 方案一（字格营造）**三者合成一个全新核心循环，其余三个做成独立模式试水。

---

## 1. 诊断：为什么叠加融合仍然乏味

### 1.1 问题不在"融合数量"，在"融合的语义层级"

现有融合的实际作用链路是：

```
玩家放置「火」+「火」→ 得到「焱」→ 数值变强
```

这里「焱」只是一个**名字更好听、数值更高的火塔**。融合的结果不改变玩家的**决策结构**——玩家依然是在"哪里放塔、放哪种塔"这个二维平面上做优化。这是所有同质化塔防的共同特征：**内容增量 ≠ 体验增量**。

### 1.2 传统塔防已被锁死的三根支柱

用户点名的三个"固有模式"，对应三根支柱，必须逐根拆：

| 支柱 | 现状 | 后果 |
|---|---|---|
| **固定路线** | 路径是静态数组，玩家无法干预 | 玩家的空间决策被地图预先决定，只剩"往哪塞塔" |
| **建塔防守** | 防线 = 离散的、静态的点 | 防御是被动的、无叙事的、可穷举的 |
| **波次进攻** | 敌人按时间表推进 | 玩家在波间"等待"，节奏由系统掌握而非玩家 |

### 1.3 破局原则

1. **动词优先于内容**：先问"玩家能做什么新动作"，再问"加了什么新塔"。
2. **一字一规则**：每个新系统必须能用一句中文说清，且这句话本身要体现文字逻辑。
3. **不新建系统，重写语义**：优先复用已有的相邻检测（`js/fusionSystem.js`）、标签动作（`fusion.js` 的 `resolveActions`）、墨渲染（`js/inkRenderer.js`）。

## 2. 六个创新方案

每个方案按固定结构展开：**一句话主张 → 机制细节 → 玩家动词变化 → 攻击哪根支柱 → 与现有系统的关系 → 实现路径 → 风险**。

---

### 方案一：字格营造（多格字形结构）

**一句话主张**：塔不再是"一个格子里一个字"，而是"几个格子共同构成一个字"，**字的结构即防御拓扑**。

**机制细节**

把 20×9 网格（`CELL_SIZE = 48`）视为"字格纸"。玩家在相邻的 2–4 格上落笔画，共构一个汉字，字形结构决定功能：

| 结构 | 例字 | 功能逻辑 |
|---|---|---|
| 左右 | 林、明 | 双路并行，同时覆盖两条通道 |
| 上下 | 炎、岳 | 纵向叠加，射程/穿透累加 |
| 包围 | 囚、囿 | 内圈捕获，把敌人困在字框内 |
| 品字 | 鑫、森、淼 | 三格联动，共享冷却与增益 |

**与现有融合的区别（关键）**：现有融合是"两塔 → 一格"的**收缩**；字格营造是"多格 → 一字"的**铺开**。两者语义正交，可共存为两层建造体系：先用字格铺出"复合字"，再用融合把复合字与邻字并成"词"。

**玩家动词变化**：放置（点）→ **构形（连线/勾勒）**

**攻击支柱**：建塔防守

**实现路径**
- 新增 `js/config/glyph.js`：`GLYPH_LAYOUT` 表，字形 → 占格模板（如 `{ char: '林', cells: [[0,0],[1,0]], structure: 'leftright' }`）。
- 网格数据结构从"格 = 塔"扩展为"格 = 笔画槽位 + 所属字的 id"。
- `js/entities/towers/` 需要一个 `CompoundGlyphTower`，它持有多个槽位的攻击配置。
- 渲染复用 `inkRenderer` 的飞白/墨晕，按结构绘制部件间的连接笔意。

**风险**：占格冲突与玩家空间计算负担；与现有融合的单格模型存在架构冲突，必须先做"共存决策"。

### 方案二：句读改径（标点即地形编辑器）

**一句话主张**：地图是一篇文章，敌人沿**字序**流动；玩家放置**标点**改变断句，从而改变敌人走哪条路。

**机制细节**

敌人不再是"沿固定路径数组移动"，而是"沿着玩家书写的字链阅读前进"。标点是地形编辑工具：

| 标点 | 效果 |
|---|---|
| 「。」 | 终止当前流，敌人转向前一字符方向 |
| 「、」 | 并列分流，本段敌人按比例分成多股 |
| 「？」 | 该段敌人原地"质疑"僵直 1 秒 |
| 「！」 | 该段敌人加速冲刺，但同时受到额外伤害 |

**这直接废除了"固定路线"**：路径成为玩家可书写的对象，每一关的地图变成一篇可改写、可重新断句的文本。

**玩家动词变化**：放置炮塔 → **断句（编辑路径）**

**攻击支柱**：固定路线

**实现路径**
- `js/data/levels/` 的关卡数据从 `path: [[gx,gy],...]` 升级为 `text: { chars: [...], punctuation: [...] }`。
- `js/entities/enemy/` 的移动逻辑需从"沿数组前进"改为"沿字序图寻路"（BFS/Dijkstra 到核心字）。
- **必须新增路径合法性校验器**，防止出现无解路径（可参考现有山字塔的路径校验逻辑，它是唯一放在路径上的塔）。
- 建议**分两阶段**：轻量版只改"入口分流权重"，不动寻路核心；验证玩家是否真正买账后，再决定是否做全量图寻路。

**风险**：这是唯一触及敌人核心移动逻辑的方案，回归风险最高；动态寻路容易出现"敌人绕路刷怪"或"路径无解"。

**独特性评价**：中文的"句读"是全世界文字系统中极为特殊的存在（一句话因断句不同而意义反转），这是其他语言做不出的机制。

### 方案三：语法羁绊（组词成句的规则编译器）

**一句话主张**：把现有的"相邻 → 融合"升级为"**相邻 → 成词 → 成句**"的三层规则编译器，**词性与句法决定增益类型**。

**机制细节**

| 层级 | 单位 | 规则 |
|---|---|---|
| 层一 · 字 | 单塔 | 现有 12 系基础塔能力 |
| 层二 · 词 | 相邻 2 塔 | 结构决定增益：偏正（火+山=火山）→ 修饰语加强中心语；并列（金+木）→ 双属性平分；动宾（火+专攻「尸」）→ 对指定敌种特攻 |
| 层三 · 句 | 沿路径 3–4 字 | 成序触发"句法技"：如「火 烧 连 营」需四字按序排布，触发全路径持续灼烧 |

**玩家动词变化**：不变（放置/融合），但**决策空间从"塔组合"升级为"句法规划"**——玩家要思考的不是"放什么"，而是"这句话怎么读通"。

**攻击支柱**：建塔防守（把"防线"从点集升级为"文本结构"）

**实现路径**（**可行性最高的方案**）
- 现有 `js/fusionSystem.js` 已实现相邻检测，`js/config/fusion.js` 已有 `resolveActions(components, desc)` 标签动作系统。
- 改动集中在两处：把"两两融合"改为"**区域扫描 + 语法图构建 + 增益结算**"；`js/config/` 新增 `GRAMMAR_RULES` 表（词性判定 + 句法技）。
- **不需要**改渲染、不需要改敌人、不需要改资源系统。

**风险**：规则可读性——玩家看不懂语法就会变成"玄学数值"。必须配套 UI 可视化（用细连线与结构框实时显示当前生效的词与句，复用现有水墨线条风格）。

**协同价值**：本方案定义了「词」「句」这两个概念，**方案二（句读）与方案五（对句）都以它为前提**。因此它是整个创新体系的公共底座。

---

### 方案四：墨为血（浓淡干湿的资源与自侵蚀）

**一句话主张**：金币换成「墨」，**墨量同时是货币与生命**，字会随时间晕染、扩散、干涸。

**机制细节**

- **墨量 = 货币 + 生命**：写字耗墨，敌人不直接扣核心血，而是**擦除你的墨与笔画**。写多必枯，形成天然张力。
- **浓墨 / 淡墨**：浓墨写的字更强，但会向邻格晕染，污染相邻字（降效甚至误伤）；淡墨字弱但可写更多。这是一个**主动的风险权衡**，而不是数值升级。
- **干涸**：长时间不攻击的字会"枯"，需要"蘸墨"补给 —— 让玩家的注意力持续分布全图，而非只关注热点。
- **残字降级**：字被擦掉笔画后**功能降级**（举例：「火」少了上面两点，就不再是「火」），把"血条"这一抽象概念换成**可肉眼观察的字形完整性**。

**玩家动词变化**：购买升级 → **蘸墨、权衡浓淡、修复笔画**

**攻击支柱**：建塔防守 + 波次进攻（把"等波次"变成"养护文本"）

**实现路径**
- 新增墨资源层，替换 `js/game.js` 中的金币逻辑（或与之并存为双资源）。
- `js/inkRenderer.js` 需增加"扩散 / 干涸 / 残留"三种字状态渲染（现有墨晕、飞白、拖影可复用）。
- 字体的"残缺渲染"需要按笔画拆解 —— 这是本方案最大的技术工作量。

**风险**：两个资源耦合会导致数值平衡难度指数上升；纯黑白画面下"浓淡"的表达需要依赖透明度与墨点密度，UI 需专门设计。**项目已有 `npm run test:balance` 回归基线，本方案的数值重调必须一次性完成，反复改会拖垮测试基线。**

**战略价值**：这是唯一一个**把美术语言直接变成规则语言**的方案——水墨的"浓淡干湿"从装饰变成玩法，是差异化最深的一层。

### 方案五：对句波次（以文会友的节奏重构）

**一句话主张**：把"波次倒计时"变成"**应答创作**"——敌出上联，玩家对下联，**对仗工整度决定这波的难度与奖励**。

**机制细节**

- 敌方每波"出上联"（在屏幕上以竖排文字出句）。
- 玩家必须在限定时间内，在网格上用塔/字**组成下联**。
- 判定维度（建议只做前三项，**不做平仄**）：字数、词性、意象标签、结构。
- 结果反馈：
  - 对仗工整 → 敌人自乱（互相攻击、掉血）、奖励倍率提升
  - 对仗失工 → 敌人强化，波次更难
- 这把"被动等待"变成"主动创作"，让每一波都是一次小型文学挑战。

**玩家动词变化**：等待 → **应答（对句）**

**攻击支柱**：波次进攻

**实现路径**
- 需要一套**策划表维护的意象词库**（同义/同类标签映射），以及一套宽容度可调的判定函数。
- **绝对不要用 LLM 实时判定**：延迟与成本不可控，且玩家无法预测结果。用确定性规则表。
- 强烈建议做成**独立模式**（项目已有 `js/modes/conquest/` 独立模式架构，可直接复用其关卡流程骨架）。

**风险**：判定宽容度极难调 —— 过严变成"语文考试"，过宽变成"摆设"，中间地带很窄；内容成本是六个方案中最高（词库 + 关卡设计）。

**独特性评价**：新颖度与文字契合度双双满分。对仗是中文独有的、有明确形式规范的文字游戏，且天然与"排布单位"这个塔防动作同构。

### 方案六：错别字入侵（敌人作为编辑者）

**一句话主张**：敌人不再只是"扣血"，而是**篡改你的字**——防守目标从"血条"变为"**语义完整性**"。

**机制细节**

敌方单位携带偏旁/笔画，靠近你的塔时尝试"改写"：

| 原字 | 被改写 | 结果 |
|---|---|---|
| 火 | 火 + 虫 → 烛 | 攻击降级（被削弱） |
| 木 | 木 + 木 → 林 | 意外强化（机会窗口） |
| 山 | 山 + 石 → 岩 | 属性改变 |

- 玩家需要**校勘**（点击修复）或**誊抄**（重写该字，消耗墨）。
- 核心是一个「文」字，被改坏则失败 —— **失败条件从数值变为语义**。
- 双向设计（既可能被削弱也可能被意外强化）是防止挫败感的关键：让"错别字"成为风险与机会并存的变量，而不是纯粹的惩罚。

**玩家动词变化**：放置炮塔 → **校勘、誊抄、防护语义空间**

**攻击支柱**：建塔防守

**实现路径**
- 可复用 `js/config/fusion.js` 的映射思路（字 + 偏旁 = 新字），但需要一个**更宽的"字 + 偏旁"映射表**，而非仅仅元素融合表。
- 敌人需要"篡改意图"AI：优先级判定（改哪个字收益最高）。
- 渲染需支持"半成品字"（一个字只显示部分笔画）。

**风险**：这是六个方案中**玩家理解成本最高**的（"为什么我的塔突然变弱了？"）；负面机制天然挫败，对视觉反馈质量要求极高。**建议不要作为全局规则，而是做成特定敌人（"错字鬼"）的专属机制或 Boss 战设计。**

## 3. 横向对比

| 二 · 句读改径 | ● | | | 空间/路径 |
| 三 · 语法羁绊 | | ● | | 规则语义 |
| 四 · 墨为血 | | ● | ● | 资源模型 |

| 六 · 错别字入侵 | | ● | | 对抗/失败条件 |

六个方案在"改变的维度"上互不重叠，这也是它们可以**叠加而非互斥**的前提。

### 3.3 关键取舍说明

- **加权分 ≠ 实施顺序**。方案五（对句波次）加权分排名第二，但内容成本与判定调优风险使其**不适合作为第一步**。加权分衡量的是"设计价值上限"，优先级衡量的是"实施顺序"。
- **方案三与方案四必须同批做**。两者都要求全量数值重调（前者改增益结算，后者改资源层），分两次做会让平衡基线被推翻两次。项目已有 `npm run test:balance` 回归测试，同一窗口内完成可显著降低验证成本。
- **方案二与方案五的风险性质不同**。方案二的风险是**技术性**（寻路改造，可工程化解）；方案五的风险是**调优性**（判定宽容度，靠测试迭代才能收敛）。

## 4. 推荐优先级与路线图

### 4.1 第一推荐：三 + 四 + 一 合成新核心循环

单独做任何一个方案都只是"加了一个新系统"；三者叠加时，核心循环会发生**质变**：

```
现状：  放塔 → 融合 → 打怪 → 放塔 → 融合（同义反复）

三+四+一：
       蘸墨 → 写字（字格营造，多格构形）
            → 成词（语法羁绊，词性增益）
            → 成句（句法技，序列触发）
            → 校勘（墨为血，字被擦蚀需修复）
            → 蘸墨 …
```

这是一个**以文字为第一性**的循环：资源是墨（书写介质），单位是字（书写结果），规则是语法（书写规则），失败是字被擦坏（文本损毁）。它不再是"套了文字皮肤的传统塔防"。

### 4.2 分阶段路线图

| 阶段 | 内容 | 交付形态 | 关键理由 |
|---|---|---|---|
| **P0** | 方案三 · 语法羁绊 | 主线新增"语法试炼"关（参考坐标：第 5 关「墨分五色」），不推翻现有主线 | 依赖最少、复用现有相邻检测与标签动作；是方案二/五的公共底座 |
| **P1** | 方案四 · 墨为血 + 方案一 · 字格营造 | 合并为一次数值重调窗口 | 避免平衡基线被推翻两次；三者共同构成新核心循环 |
| **P2** | 方案二 · 句读改径（**轻量版先行**） | 独立模式或第 7+ 关 | 体验独特性最高但回归风险最大；先用"标点改入口分流权重"验证玩家接受度，再决定是否做全量图寻路 |
| **P3** | 方案五 · 对句波次 | **独立模式**（复用 `js/modes/conquest/` 架构） | 内容成本最高、判定调优最难，但新颖度满分；适合作差异化卖点与宣传素材 |
| **P3** | 方案六 · 错别字入侵 | **特定敌人"错字鬼"或 Boss 战专属机制** | 负面机制需要极高反馈质量，不宜作为全局规则 |

### 4.3 最小验证原型（建议第一步就做）

用最小的工程量验证"文字内核能否成为第一性"这个核心假设：

1. 在一张现有地图上，**不新增任何塔**，仅实现方案三的"层二 · 词"：两塔相邻时按偏正/并列/动宾结构给出不同增益，并在 UI 上用水墨连线标出当前生效的词。
2. 观察指标：玩家是否**主动**为了凑"词"去调整布局（而非为了数值去堆塔）。若答案是肯定的，则"文字即规则"的假设成立，可以放心推进 P1。

这个原型的价值在于：**它不依赖任何新美术、新敌人、新资源，只改变规则解释层**，是六个方案中成本最低、信息量最高的一次验证。

## 6. 后续建议

1. **先做 4.3 的最小原型**，用数据而非直觉决定是否推进 P1。
2. 实施任何一项前，按 `AGENTS.md` 要求先在 `docs/工单计划/` 创建工单 —— 本文件是设计提案，不构成开发授权。
3. 注意 `AGENTS.md` 的 600 行文件上限：方案一（字格数据）与方案二（寻路）很可能需要新建模块而非扩展现有文件。
4. `js/config/fusion.js` 中已有一条"仅用于土系链式进化入口"的 `圭`，存在设计意图与文档统计口径不一致的隐患，建议在动融合系统前先统一口径。
