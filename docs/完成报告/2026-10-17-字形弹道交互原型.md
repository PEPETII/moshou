## 1. 实际完成内容

建成一套可交互的「字形 → 弹道」验证原型，用 **火、川、山** 三座塔落实「字形即弹道」，并把原始案例 **弓** 作为对照范例一并实现。

核心机制并非「把字贴图发射出去」，而是三条规则的真实落地：

| 规则 | 实现方式 |
| --- | --- |
| 可读性优先 | 字身始终正写、永不旋转；定向只改 `tw.aim`（出锋方向），由字身外缘的笔锋指示、弹道预览、弹丸几何共同朝目标展开 |
| 形义一致 | 弹道几何全部**从笔画数据推导**，逻辑层没有硬编码任何方向 |
| 笔顺即时序 | 每写完一笔才放出一发；笔顺天然就是攻击节奏，起笔即前摇、收笔即出招、`cd` 即回锋 |

四座塔的「字形 → 弹道」映射：

- **火（四笔放射）**：每笔沿该笔自身的收笔走向迸出一粒火星，四笔＝一个扇形；短射程、低单发、高覆盖。
- **川（三竖并列）**：三条平行水流沿出锋方向贯穿，**平行间距 = 三竖字距（±13px）**；线段判定、穿透全部、附着「湿」减速。
- **山（三峰并立）**：三块墨岩落在出锋线上，**横向跨度 = 三峰间距、弧高 = 峰高**；三点排开覆盖整条路宽，落点圆判定。
- **弓（弓臂 + 隐含弦）**：弦的弯曲度 = 蓄力值，直接决定初速与穿透层数（2～5 层，每层 ×0.82）。

## 3. 关键实现

### 3.1 字形不用字体，用笔画折线

每个字由 3～4 条折线定义（`pts`）+ 三段笔压（`w = [起笔, 行笔, 收笔]`）。这样做有两个好处：

1. **不依赖运行环境的字体**，任何机器渲染结果一致；
2. **笔画自带几何信息**——收笔切线就是弹道方向，横向均值就是平行弹道的间距，最高点就是抛投弧高。

`Ink.analyze()` 一次性导出每笔的 `dir / cx / topY`，`firePayload()` 只做「旋转 + 取用」，因此**换一个字就等于换一种弹道**，不需要改逻辑。

### 3.2 出锋方向是唯一的朝向来源

字身坐标系的「天然出锋方向」`native`（火/川/山 向下、弓向右）与目标角度 `aim` 之差即为旋转量：

```
rot = aim - native;   // 字身不转，只把弹道几何转过去
```

所以拖拽塔身时，画面上是「字不动、笔锋与弹道跟着转」——这正是原则①要证明的事。

### 3.3 笔顺驱动攻击循环

`tickCycle()` 把攻击拆成逐笔推进：每笔 `strokeDur` 秒，`prog` 到 1 才 `firePayload(idx)`，四笔写完才进入冷却。书写中的那一笔以高墨色叠加，写完的笔画在 0.85s 内褪回底色，形成「这个字正在被重新写一遍」的观感。

弓是特例，用状态机：`idle → draw（张臂，弦随蓄力后拉）→ nock（搭箭）→ loose（撒放，出矢）→ recover`。

### 3.4 水墨观感

- 笔锋：按 1.4～3 单位步长重采样，逐段描边并插值线宽，收笔段随机断笔形成飞白；
- 飞白强度可调（`dry` 参数）：大尺寸字形放开，50px 塔身压到 0.22，避免笔画碎成虚线；
- 塔座用径向渐变墨托，避免字浮在纸上；
- 命中反馈分档：矢＝顺弹道方向的飞白「笔锋」，水＝环形涟漪，火＝墨点溅射，山＝落点墨渍 + 冲击环。

## 4. 测试 / 验证结果

用 Playwright（Chromium headless）加载 `file://` 页面并逐帧截图核对：

- **控制台零报错**（`pageerror` / `console.error` 均为空）；
- 四塔均能自动索敌、逐笔开火，击杀累积正常（验证中多次观察到 6～10 杀）；
- 拖拽火塔：`aim 1.75 → -0.14`，`manual = true`，字身视觉不旋转、只有弹道随动；
- 模式切换（密集队列 / 常规 / 精英）与齐射、重播笔顺、暂停均正常；
- `npm run check:line-count` 通过：扫描 143 个文件，最大 585 行，本次新增文件全部 ≤ 466 行。

过程中修复的关键缺陷：

1. **`strokeDur` 缺失**：四塔配置里漏了单笔时长，导致 `prog = t/undefined = NaN`，所有塔永不发射。这是首轮截图「只有塔不开火」的根因。
2. **小尺寸飞白过度**：50px 塔身的笔画被打断成虚线，字不可读 → 增加 `dry` 系数。
3. **水流被画成「香肠」**：三段粗描边无收束 → 改为带渐变填充的实体水带（尾部化开、头部饱满）。
4. **抛投弧高过大**：墨岩飞出画面上缘像在天上漂 → 弧高由 `56+74h` 收到 `38+48h`，并把起手点挪到字身外缘。

## 5. 未解决问题

1. **未做真实设备手感测试**：仅做了无头渲染与交互事件验证，触屏拖拽（`pointer` 事件）在移动端的实际体验未实测。
2. **数值未与正式工程对齐**：原型数值（伤害、射程、节拍）是按「看得清」而非「平衡」设定的，不构成平衡建议。
3. **火塔的散射吃亏**：四笔方向由字形固定，最外侧两笔天然偏离出锋方向较多，实测有相当比例火星打空。这是「形义一致」的代价还是需要收敛扇角，需要试玩判断。
4. **只覆盖 4 个字**：字库扩充（如矛、乂、网、雷）时，`native` 与笔画裁切规则是否够用尚未验证。

## 6. 后续建议

1. **先做「关掉预览」的盲测**：让 3～5 人各玩 60 秒，问「川会怎么打」，能答对再谈落地。
2. **单笔时长做 A/B**：`strokeDur` 0.10 / 0.16 / 0.22 三档，观察是「笔意更清楚」还是「节奏拖沓」。
3. 若验证通过，正式接入时建议把 `GLYPHS` 数据迁到 `js/config/` 的独立域文件，`firePayload` 的四种几何分支抽成 `js/entities/towers/` 下的策略模块，避免 `tower.js` 继续膨胀。
4. 出锋方向建议保留手动，但加「吸附到最近敌群」的辅助，降低操作成本。
