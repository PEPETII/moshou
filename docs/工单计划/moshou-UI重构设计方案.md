# 《墨守成规》UI 重构设计方案

> 项目：PEPETII/moshou  
> 类型：纯前端 HTML5 Canvas + CSS + JavaScript 水墨文字塔防游戏  
> 设计目标：在保留“汉字 + 水墨 + 塔防”核心识别度以及现有浅色宣纸画布的前提下，将偏“网页组件化”的 UI，升级为真正具有游戏世界观与沉浸感的水墨游戏界面。  
> 当前基础色板：画布纸底 `#f4efe4`、网格线 `#ded5c0`、敌人/主文字 `#1c1a17`、辅助文本 `#6a6459`。

---

## 一、设计目标

《墨守成规》的核心不是“一个带中国风皮肤的网页塔防”，而应该是一款：

> **会动的水墨古籍。**

整个 UI 必须围绕以下三个核心建立：

1. **汉字既是内容，也是图标与视觉主体**；
2. **水墨不是背景装饰，而是整个界面的交互语言**；
3. **UI 必须像游戏，而不是像网站、SaaS、Dashboard 或普通移动 App。**

---

# 二、最终视觉定位

## 2.1 核心风格

建议统一为：

> **宣纸长卷 · 浓淡墨 · 朱印**

整体视觉关键词：

- 浅色宣纸
- 浓墨 / 淡墨
- 飞白
- 毛笔汉字
- 朱砂印章
- 山水长卷
- 古籍排版
- 墨迹扩散
- 不规则边缘
- 大量留白
- 克制动效

## 2.2 风格原则

不是简单地使用浅色背景和书法字体，而是让所有 UI 元素都像真实落在同一张宣纸、同一册古籍、同一幅水墨长卷中。

界面中的：

- 按钮
- 面板
- 选中状态
- 提示
- 关卡入口
- 图鉴
- 融合
- 胜负反馈

都应该使用“墨、纸、字、印”来表达，而不是标准 Web 组件。

---

# 三、当前 UI 的主要问题

当前项目本身的题材和玩法识别度已经足够明显，而且现有画布纸底已经具备正确的“宣纸 + 墨”基础。真正需要解决的不是把画面改成深色，而是减少网页组件感，主要表现为：

- 宣纸底之上仍大量使用规则矩形卡片/面板；
- 部分界面视觉层级主要依赖边框、圆角、阴影，而不是墨色浓淡、留白和题字关系；
- 常规 Card 结构；
- `border-radius` 圆角卡片；
- 普通 `box-shadow`；
- `linear-gradient`；
- Hover 上浮；
- 标准 Modal；
- Emoji 充当图标；
- 图鉴采用网格卡片；
- 关卡采用普通按钮 / 卡片列表；
- 资源信息使用标准顶部状态栏。

这些表现虽然“好看且可用”，但更接近：

> 中国风主题网页

而不是：

> 汉字构成的水墨游戏世界

---

# 四、颜色体系

## 4.1 现有基础色板必须保留

本次 UI 重构**不改变当前画布的浅色宣纸基调**。以下颜色视为项目基础色板，后续设计应围绕它们扩展，而不是重新建立一套深色主题。

| 视觉角色 | 当前颜色 | 用途 |
|---|---|---|
| 画布纸底 | `#f4efe4` | 战场、主界面纸张底色，是整个项目的基准色 |
| 网格线 | `#ded5c0` | 战场网格、弱分隔线、纸面结构线 |
| 浓墨 | `#1c1a17` | 敌人、主文字、核心汉字、主要线条 |
| 辅助墨 | `#6a6459` | 辅助文本、说明、次级信息 |

其中敌人与主文字共用 `#1c1a17` 是合理的：游戏应优先通过**字号、字形、墨迹浓度、动态和空间位置**区分敌我与信息层级，而不是依赖大量不同颜色。

## 4.2 建议新增的有限扩展色

为支持印章、状态和纸张层次，可以增加少量辅助色，但不能破坏现有纸墨关系。

| 视觉角色 | 建议颜色 | 用途 |
|---|---|---|
| 纸张阴影 | `#e8e1d2` | 宣纸叠层、浮纸、卷轴边缘 |
| 淡墨 | `#9b9386` | 禁用、锁定、次要装饰、远景墨迹 |
| 朱砂 | `#b4473a` | 印章、核心危险、关键确认、重要战斗状态 |
| 暗朱砂 | `#7d342c` | 朱砂按下态、裂印、低生命状态 |
| 古金（可选） | `#a88c52` | 奖励、稀有、货币；必须极少使用 |

## 4.3 颜色使用原则

- `#f4efe4` 是默认世界底色，不得因为 UI 重构被大面积深色面板覆盖；
- `#1c1a17` 是最重要的“墨”，负责主要文字、敌人和关键轮廓；
- `#6a6459` 负责信息降级，不额外引入普通网页灰色体系；
- `#ded5c0` 适合网格与弱分隔，不应升级成醒目的卡片边框；
- 朱砂只承担**印章、危险、关键确认、核心状态**，不能沦为普通按钮主题色；
- 金色只用于奖励/货币/稀有内容，可不用则不用；
- 禁止蓝紫渐变、霓虹发光、大面积高饱和彩色；
- UI 层级优先通过“墨的浓淡、字的大小、留白、纸张叠层”建立，而不是不断新增颜色。

# 五、图标体系

## 5.1 禁止 Emoji 作为正式图标

当前例如：

- 🏯 炮塔图鉴
- 👹 怪物图鉴
- ⚡ 融合图鉴
- ⚔️ 自定义炮塔
- 🗺️ 自定义关卡
- 💾 导入导出

正式 UI 中应逐步替换。

## 5.2 汉字即图标

推荐：

### 炮塔图鉴

```text
    塔
  炮塔志
───────
御敌诸字录
```

### 怪物图鉴

```text
    鬼
  妖异录
───────
来犯诸邪
```

### 融合图鉴

```text
 火 + 山
    ↓
   火山

 合字谱
```

整个项目应强化：

> **字就是图标。**

# 六、主菜单设计

## 6.1 现有问题

当前结构接近：

```text
墨守成规

[图鉴]
[塔防模式]
[征服模式]
[自定义]
```

功能清晰，但网页菜单感较强。

## 6.2 推荐结构

```text
          墨
       守 成 规

    ─── 朱印 ───

         塔 防
      「守一方墨境」

         征 服
      「拓四方疆土」

          图 鉴

          自 定

           设
```

## 6.3 主菜单动画

首次进入建议：

1. 空画面；
2. 墨滴落下；
3. 墨迹扩散；
4. “墨守成规”四字以书写形式逐步出现；
5. 最后一笔完成；
6. 朱砂印章落下；
7. 菜单逐项显现。

动画重点：短、克制、有仪式感。

---

# 七、按钮系统

## 7.1 避免标准矩形按钮

普通按钮：

```text
┌─────────┐
│ 开始游戏 │
└─────────┘
```

建议改为“题字式按钮”：

```text
  开 始
────────
```

默认弱边界或无边界。

## 7.2 Hover / Active

Hover：

- 底部出现墨线；
- 文字轻微变亮；
- 墨迹轻微扩散。

Active：

- 字体轻缩；
- 墨线加深；
- 不使用网页式高光。

## 7.3 选中状态

不建议使用蓝光 / 金色 Glow。

可使用：

- 朱砂小印；
- 一圈墨晕；
- “选”字印；
- 不规则墨圈。

---

# 八、战斗 HUD

## 8.1 目标

HUD 必须极简，不占用战场，不形成顶部导航栏感。

## 8.2 推荐结构

```text
墨 · 300          第二阵          守 · 18

              尸 × 16
```

## 8.3 资源命名

可将“金币”进一步世界观化为：

```text
墨 300
```

但实际数据建议仍保留阿拉伯数字，保证移动端快速阅读。

## 8.4 核心生命

不建议使用普通 HP 条。

建议使用朱砂印：

```text
┌──┐
│守│
└──┘
18
```

生命下降时：

- 印章出现裂纹；
- 朱砂颜色变淡；
- 低血量时出现轻微扩散；
- 核心受击时印章短暂震动。

---

# 九、炮塔选择栏

炮塔栏是最应该体现《墨守成规》特色的地方。

## 9.1 现有方向

已有汉字：

- 火
- 水
- 山
- 木
- 金
- 土

应继续强化，而不是把这些汉字放进标准 Card。

## 9.2 推荐方案

```text
 火    水    山    木    金    土
 80   100   90   120   150   200
```

默认只有字 + 费用。

选中“火”后：

- 字体周围出现墨晕；
- 下方盖朱砂小印；
- 不使用标准边框卡片。

## 9.3 锁定炮塔

避免：

```text
🔒
opacity: 0.35
```

建议：

```text
木
未悟
```

或覆盖一条淡墨封条。

---

# 十、炮塔升级 / 详情界面

建议做成展开的小型“字帖 / 墨签”。

示例：

```text
           火

        壹 · 初燃

伤    1      →      2
距    5             6
势    1.0           0.9

──────────────

      「淬 字」
        墨 50

         舍
       得 70
```

## 设计原则

- 大字负责身份识别；
- 属性信息保持高可读性；
- 操作词尽量短；
- 统一采用“题字 + 墨线”的交互语言；
- 不要继续使用普通属性 Card。

---

# 十一、融合系统

融合应该成为整个游戏最有仪式感的 UI。

## 11.1 融合流程

第一阶段：

```text
火                  山
```

第二阶段：

两个字向中心缓慢靠拢，墨迹相互侵染。

第三阶段：

浓墨瞬间覆盖中心。

第四阶段：

墨迹散开：

```text
火山
```

随后出现朱砂印：

```text
「合」
```

## 11.2 原则

- 不使用普通“确认融合”弹窗作为核心体验；
- 融合应有短动画；
- 新字出现时必须产生明确反馈；
- 形成《墨守成规》的独有“合字仪式”。

---

# 十二、图鉴系统

## 12.1 不建议继续使用卡片网格

当前网格卡片会强化 Web 感。

建议改为：

> **百字谱 / 古籍翻页式图鉴。**

## 12.2 推荐布局

左侧：

```text
火
水
山
木
金
土
```

右侧：

```text
           火

      五行 · 火

伤      ●●●○○
势      ●●○○○
距      ●●●●○

「逐敌而焚，一字追一魂。」

初见：第一境
耗墨：80

──────────────

可合：
火 + 山 → 火山
火 + 水 → 蒸
火 + 木 → 炎
```

图鉴本身应成为游戏体验的一部分，而不是资料页面。

---

# 十三、关卡选择

推荐重点重做为：

> **水墨山河长卷。**

## 13.1 交互方式

- 横向拖动画卷；
- 每个关卡对应一个山、河、城关、石碑或印记；
- 不使用普通 Card Grid。

## 13.2 示例

```text
墨境入口
   │
   ● 初入墨境
        ～～山～～
                ● 墨林深处
                        △△
                         ● 金石之御
                              ~~~
                               ● 土崩瓦解
```

点击某一关后展开：

```text
第三境

金石之御

「金石为盾，锋芒为矛」

敌：
尸  鬼  甲

新悟：
金

       入境
```

# 十四、胜利与失败

## 14.1 胜利

不建议普通 Modal：

```text
游戏胜利！
下一关
主菜单
```

推荐：

1. 战场短暂停止；
2. 巨大毛笔字“胜”出现；
3. 墨汁向外扩散；
4. 小字“守境已成”；
5. 朱砂盖印“成”；
6. 最后才出现操作项。

```text
胜

守境已成

「成」

下一境      重览
```

## 14.2 失败

建议使用：

```text
破
```

或：

```text
失守
```

并让核心朱砂印裂开、墨迹散去。

---

# 十五、UI 三层结构

为了方便 Codex 和后续维护，整个 UI 建议统一分为三层。

## 第一层：战场 HUD

只保留：

- 资源；
- 波次；
- 敌人数；
- 核心状态；
- 炮塔栏。

特点：极简、常驻、不能遮挡战场。

## 第二层：即时交互

包括：

- 炮塔详情；
- 升级；
- 出售；
- 融合；
- 提示；
- 暂停。

视觉：小宣纸 / 墨签 / 墨迹浮层。

## 第三层：大界面

包括：

- 主菜单；
- 关卡；
- 图鉴；
- 征服模式；
- 自定义；
- 设置。

视觉：长卷 / 古籍 / 字帖。

---

# 十六、动效规范

## 推荐动效

- 墨迹扩散；
- 飞白显现；
- 毛笔书写；
- 印章落下；
- 字体轻微晃动；
- 墨线划过；
- 墨迹拖影；
- 宣纸浮现。

## 禁止滥用

- 大幅缩放；
- 夸张弹跳；
- SaaS 卡片上浮；
- 霓虹 Glow；
- 大面积渐变；
- 长时间复杂动画。

原则：

> 动画像“墨在动”，而不是“网页元素在动”。

---

# 十七、移动端 / 横屏适配

当前项目真实 Canvas 已以：

```text
960 × 432
20 列 × 9 行
CELL_SIZE = 48
```

作为主要实现基础。

因此 UI 重构必须以当前真实尺寸为准。

## 注意

当前 `docs/ui-design-spec.md` 中仍存在 800 × 480 的旧设计描述，应在本次重构时同步修正。

## 移动端要求

- 横屏优先；
- 触控区域 >= 44px；
- 不依赖 Hover；
- 关键信息边缘布局；
- 底部炮塔栏允许横向滑动；
- 弹层不得挡住大部分战场；
- 保证 960×432 Canvas 完整显示；
- 使用当前已有 `--ui-scale` 与触摸缩放补偿机制。

---

# 十八、明确禁止的视觉方向

正式 UI 中应避免：

- SaaS Dashboard；
- 玻璃拟态；
- 蓝紫渐变；
- 大量圆角；
- Emoji 正式图标；
- 统一矩形 Card；
- 霓虹 Glow；
- 现代管理后台布局；
- iOS 设置页风格；
- Material Design 卡片；
- 大面积与宣纸基调冲突的深色面板，或为了分层而不断叠加纯灰卡片；
- 标准网页 Modal；
- 与水墨世界观无关的常规图标库。

---

# 十九、推荐改造优先级

## Phase 1：建立视觉基础

1. 更新全局颜色变量；
2. 删除 / 弱化大量 Card；
3. 建立汉字图标体系；
4. 建立题字按钮体系；
5. 统一朱砂印章选中状态；
6. 更新 `docs/ui-design-spec.md`。

## Phase 2：主菜单

1. 重构标题；
2. 重构菜单；
3. 增加墨迹进入动画；
4. 删除 Emoji 图标；
5. 建立正式游戏第一印象。

## Phase 3：战斗 HUD

1. 重构顶部状态；
2. 重构炮塔栏；
3. 重构锁定 / 选中状态；
4. 重构炮塔详情；
5. 优化移动端触摸反馈。

## Phase 4：关卡长卷

1. 删除普通关卡 Card；
2. 制作横向水墨长卷；
3. 关卡点位融入山水；
4. 关卡信息以石碑 / 墨签方式展开。

## Phase 5：融合系统

1. 重做融合确认界面；
2. 增加合字动画；
3. 增加朱砂“合”印；
4. 强化成功反馈。

## Phase 6：图鉴

1. 改为百字谱；
2. 左侧字表；
3. 右侧古籍详情；
4. 融合关系以书谱形式展示。

## Phase 7：胜负与其他界面

1. 胜利“胜 / 成”；
2. 失败“破 / 失守”；
3. 征服模式；
4. 自定义模式；
5. 设置；
6. 加载界面。

# 二十、Codex 执行原则

在实际修改时必须遵守项目现有开发约束：

- 继续保持纯静态 HTML5 Canvas + JavaScript；
- 不引入 React / Vue / TypeScript / Vite 等；
- 每次修改前在 `docs/工单计划/` 创建工单；
- 完成后在 `docs/完成报告/` 生成报告；
- 所有代码文件原则上不超过 600 行；
- 修改前优先确认真实代码，不能只依赖旧文档；
- UI 修改不能破坏塔防核心玩法；
- 不能破坏触屏交互与移动端缩放；
- 优先通过 CSS / Canvas / 少量 DOM 调整完成视觉升级；
- 不为视觉重构引入不必要的复杂框架。

---

# 二十一、最终验收标准

完成 UI 重构后，应至少满足：

### 视觉

- 玩家第一眼可以判断这是“水墨游戏”，而不是网页；
- 不再大面积出现标准 Web Card；
- Emoji 基本退出正式 UI；
- 汉字承担主要视觉识别；
- 朱砂印章成为重要交互语言；
- 宣纸、墨迹、飞白贯穿所有界面。

### 一致性

- 主菜单、HUD、图鉴、关卡、融合、胜负属于同一个视觉世界；
- 不同界面不再各自使用不同 Web 组件风格；
- 所有选中、锁定、确认、危险状态拥有统一设计语言。

### 可用性

- 960 × 432 Canvas 不受破坏；
- 横屏移动端可正常操作；
- 重要按钮满足触控要求；
- 不依赖 Hover 才能理解状态；
- 信息层级清晰；
- 核心玩法信息依然易读。

### 游戏感

- 主菜单有明显仪式感；
- 融合有独特反馈；
- 关卡选择具有探索感；
- 胜负结果有情绪反馈；
- UI 不再像浏览器网页，而像完整游戏。
