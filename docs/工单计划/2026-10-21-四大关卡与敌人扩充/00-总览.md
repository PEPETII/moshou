## 2. 实施时采用的默认假设（用户未指定，可直接执行，在完成报告里注明）

| # | 假设 | 理由 |
|---|---|---|
| B1 | **字数决定体量**：单字 = 小怪（巨、龟、铠、饕这类重敌除外），双字 = 精英，三字 = 大精英，四字 = 首领。控场规则按字数分档（12）。 | 和「字形」主题一致，玩家看字数就能判断能不能控住它。 |
| B2 | **多字敌人分字计血**：每个字有独立血量，伤害先打最前面那个还没碎的字。一个字被打碎，这个字对应的能力就失效（「碎字」）；全部碎完才算死亡。溢出伤害全额顺延到下一个字。 | 给多字敌人一个看得见的阶段感，也让「先打碎哪个字」成为有意义的设计。 |
| B3 | 非关底小关卡仍然只需坚守到时间结束；其中出现的多字精英**不要求击杀**。 | E5 只针对关底。 |
| B4 | 征服模式**不接入**新敌人和新关卡，只受 E6（山）、E7（解锁）和刷怪器重构（要求向后兼容）影响。 | 用户的需求范围是塔防。 |
| B5 | 新敌人的能力一律用游戏时间 `dt`（秒）计时，不用 `Date.now()`。 | 暂停、顿帧（hitstop）时计时要一起停；旧敌人代码里 `stunnedEnd` 用的是 `Date.now()`，新代码不要沿用。 |
| B6 | 召唤出来的敌人在召唤者当前里程附近生成，是「敌人从入口生成」规则的唯一例外。召唤物击杀奖励固定为 1 墨。 | 防止玩家靠刷召唤物无限赚墨。 |
| B7 | 表中所有数值都是**初值**，集中写在配置里，最终以 11 的护栏和实机试玩为准，调整时在完成报告里记录。 | 数值必须可调。 |

## 4. 全局约定（每份工单都要遵守）

1. **纯静态前端**：不引入构建工具，不用 TypeScript。新增 JS 文件要同时加到 `index.html`，以及所有需要它的测试环境（`tests/helpers/glyph-env.js`、`tests/test-level-curve.js` 的 `files` 列表等）。
2. **600 行上限**：`js/config/domain-03.js` 已有 404 行，新敌人**不要**写进这个文件。新文件规划如下：

   | 新文件 | 内容 |
   |---|---|
   | `js/config/enemies-single.js` | 12 种单字敌人配置 |
   | `js/config/enemies-multi.js` | 双字、三字、四字敌人配置（字段格式见 07） |
   | `js/config/control-rules.js` | 控制分档、卷入预算等（12） |
   | `js/config/boss-battle.js` | 首领出场、决战、到达核心的规则（01、10） |
   | `js/entities/enemy/abilities/*.js` | 敌人能力实现，按组拆分（07） |
   | `js/entities/enemy/segments.js` | 多字分段的血量与渲染 |
   | `js/glyph/control-rules.js` | 控制判定的运行时接口（12） |
   | `js/core/boss.js` | 首领流程（出场、到达核心、胜负） |
   | `js/ui/boss-bar.js` | 首领血条 |
   | `js/data/levels/part-01.js` ～ `part-04.js` | 每个大关卡一个文件 |

3. **配置集中**：所有数值放进 `CONFIG`，招式和能力代码里不写死数值。
4. **加载顺序**：`enemies-*.js` 必须放在 `glyph-battle.js` **之前**加载，否则 `speedPx → speed` 的换算循环覆盖不到它们；或者把这段换算循环抽成函数，在所有敌人配置加载完以后再调用（推荐后者）。
5. **键名**：敌人 key 一律用小驼峰英文（如 `bone`、`yaksha`、`baiguiyexing`），显示字放在 `char`，多字敌人的显示字放在 `segments[].char`。
6. **旧敌人配置**：`domain-03.js` 里还留着大量没有出场的旧敌人（甲、分、影、霸……）。新方案**不复用**这些 key，也不在本次删除它们；新 key 不能和旧 key 重名。
