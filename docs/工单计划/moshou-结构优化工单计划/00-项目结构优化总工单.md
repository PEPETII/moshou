# 《墨守成规》项目结构优化总工单

- 项目：`PEPETII/moshou`
- 日期：2026-09-16
- 类型：结构治理 / 技术债务 / 面向未来扩展
- 执行原则：渐进式重构、行为保持、分阶段验收、可独立回滚

## 1. 任务目标

本轮不是简单移动文件，而是建立一个适合继续扩展《墨守成规》的长期结构：

1. 梳理当前项目真实依赖、入口、全局对象、加载顺序和超大文件。
2. 将 HTML、CSS、游戏核心、实体、系统、渲染、UI、模式、数据、测试、工具脚本按职责重新组织。
3. 逐步拆分超过 600 行的代码文件，并避免产生新的“大一统”文件。
4. 保持项目为纯静态 HTML5 Canvas + JavaScript，不引入 Vite、Webpack、TypeScript 或其他构建工具。
5. 保持 `index.html` 为唯一页面入口，但让其回归“页面骨架 + 资源装配”职责。
6. 为后续增加炮塔、敌人、关卡、融合配方、征服模式内容、存档版本升级等功能预留稳定扩展点。
7. 建立测试、文档、工单、完成报告和架构文档的统一归档规则。

## 2. 当前结构事实与主要问题

根据当前仓库主分支：

- 根目录存在 `index.html`、`generate-posters.js`、`test-balance.js`、`test-fusion-recipes.js`。
- `index.html` 体积较大，同时包含外链 CSS、内联 `<style>` 和大量页面结构。
- `css/style.css` 为单一大型样式文件。
- `js/` 中已经有一定模块拆分，但仍存在明显的大文件：
  - `js/tower.js`
  - `js/ui.js`
  - `js/config.js`
  - `js/game.js`
  - `js/enemy.js`
  - `js/conquestGame.js`
  - `js/levelsData.js`
- 当前页面通过多个普通 `<script src="...">` 顺序加载，模块之间存在隐式的全局依赖与加载顺序约束。
- `docs/` 已经存在设计、审计、测试结果、工单计划和完成报告，但不同类型文档仍混放在同一层级。
- `package.json` 当前主要提供 Playwright 开发依赖，尚未形成统一的脚本入口。
- `AGENTS.md` 已要求：
  - 每个任务先创建 `docs/工单计划/`；
  - 完成后创建 `docs/完成报告/`；
  - 代码文件原则上不超过 600 行；
  - 保持纯静态前端，不擅自引入构建工具或 TypeScript。

历史审计文档中的行数只能作为参考，执行本工单时必须以当前代码重新统计，不能直接使用旧报告作为最终依据。

## 3. 重构原则

### 3.1 必须遵守

- 不改变现有玩法和数值，结构优化阶段禁止顺手调整平衡性。
- 不同时重写多个核心系统。
- 每个阶段都必须能单独运行、测试、提交和回滚。
- 拆文件优先按“职责”拆分，不按“凑够 600 行”机械切割。
- 不通过压缩代码、删除注释、合并语句规避 600 行限制。
- 所有资源路径、脚本加载顺序、DOM ID/class、Canvas 尺寸和存档 key 在未明确迁移前保持兼容。
- 不直接删除旧实现；完成迁移、测试和引用确认后再删除。
- 所有阶段开始前创建对应工单，结束后创建完成报告。

### 3.2 短期不做

- 不迁移到框架。
- 不引入 npm 打包流程。
- 不强制改成 TypeScript。
- 不在结构重构中重做 UI 视觉。
- 不在结构重构中修改游戏数值。
- 不同时进行大规模玩法开发。

## 5. 分阶段执行顺序

| 阶段 | 工单 | 目标 | 是否允许行为变化 |
|---|---|---|---|
| Phase 0 | `01-结构审计与依赖基线.md` | 获取真实结构、依赖和测试基线 | 否 |

| Phase 2 | `03-JavaScript核心模块拆分.md` | 拆分超大 JS 与隐式职责 | 否 |

## 6. 核心迁移策略

### index.html

目标：仅保留页面语义骨架、Canvas 容器、必要 DOM 节点和资源引用。

应迁出：
- 大段内联 `<style>`；
- 可独立维护的初始化逻辑；
- 与某个页面/组件强绑定的样式。

不得为“变短”而动态生成所有 DOM；HTML 仍应保持可读和可调试。

### config.js

不要简单切成 `config1.js/config2.js`。

应按配置领域拆分：
- 游戏规则；
- 炮塔；
- 敌人；
- 融合；
- 颜色/表现参数。

迁移期间保留 `window.CONFIG` 兼容入口，避免一次修改全部调用方。

### tower.js

优先拆职责，而不是按炮塔名称任意切割：

- 基础 Tower 生命周期；
- 攻击/目标选择；
- projectile；
- 状态/技能；
- 绘制；
- FusionTower；
- 融合技能执行。

拆分后不得出现双向依赖链。

### ui.js

建议按交互场景拆分：

- 输入与指针/触摸；
- HUD；
- 塔详情/升级；
- 融合确认；
- 菜单与页面切换；
- 通用 Modal。

事件绑定必须有清晰 owner，并支持重复初始化安全或显式 destroy。

### game.js

`Game` 保留编排职责，不继续吸收业务细节。

逐步移出：
- 纯数据处理；
- 可独立系统逻辑；
- 与某个具体 UI 组件强耦合的行为；
- 可由 Level/Combat/Progression system 管理的逻辑。

## 7. 依赖治理

Phase 0 必须绘制当前脚本依赖图。

短期采用：
1. 保持普通 `<script>` 加载；
2. 明确依赖顺序；
3. 通过命名空间/全局注册表降低“谁先加载都不知道”的风险；
4. 拆分完成后再单独评估原生 ES Modules。

不得在同一工单中“拆文件 + 全量迁移 ES Modules”。

## 8. 600 行治理规则

执行脚本统计全部 `.js/.css/.html` 行数。

对于 >600 行代码文件：
1. 记录职责；
2. 标出可分离区域；
3. 列出依赖；
4. 分批迁出；
5. 每迁出一块立即跑测试；
6. 原文件下降到 600 行以内后再关闭对应任务。

对于数据文件，如果大量行数来自静态关卡数据，也应优先按关卡/模式拆分，而不是继续堆在单文件。

## 9. 测试基线

至少建立以下 smoke checklist：

- 页面正常加载，无 console error。
- 主菜单正常。
- 塔防模式进入/退出正常。
- 征服模式进入/退出正常。
- 关卡选择、开始、暂停、重开正常。
- 六类基础塔正常放置。
- 山塔路径规则正常。
- 炮塔升级/出售正常。
- 融合预览、确认、取消正常。
- 敌人生成、移动、受伤、死亡正常。
- 分裂/飞行/重甲等特殊敌人行为正常。
- 胜利/失败流程正常。
- 返回菜单后再次开始无重复事件。
- `node test-balance.js` 通过。
- `node test-fusion-recipes.js` 通过。
- 如已有 Playwright 用例，必须全部通过。

## 10. 回滚要求

每个 Phase 独立提交。

建议提交粒度：

```text
refactor(structure): establish architecture baseline
refactor(html): extract inline page styles
refactor(css): split styles by responsibility
refactor(config): split configuration domains
refactor(tower): extract projectile and rendering responsibilities
refactor(ui): split input hud and dialogs
chore(test): reorganize test entrypoints
docs(architecture): update project structure and dependency map
```

不要把全项目结构优化压成一个提交。

## 12. 禁止事项

- 禁止边重构边重做玩法。
- 禁止一次性重写 `tower.js` 或 `ui.js`。
- 禁止通过全局搜索替换后未验证就删除旧代码。
- 禁止仅根据旧文档判断真实依赖。
- 禁止为了“架构漂亮”增加无实际职责的空层级。
- 禁止引入构建工具来解决本可由原生 JS 结构治理解决的问题。
