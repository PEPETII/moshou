# Phase 4 工单：未来扩展架构准备

## 任务目标

在完成结构治理后，为项目未来增加内容和玩法做好接口准备，让“新增内容”尽可能只新增数据/模块，而不是持续修改大型核心文件。

## 设计目标

未来常见需求可能包括：

- 新炮塔；
- 新融合塔；
- 新敌人；
- 新状态效果；
- 新关卡；
- 新征服内容；
- 新游戏模式；
- 存档字段升级；
- 更多 UI 面板；
- 调试和性能监控。

本工单不要求一次实现这些功能，而是建立可扩展边界。

## 1. 内容注册边界

建议逐步建立稳定 registry 概念：

```text
Tower definitions
Enemy definitions
Fusion recipes
Level definitions
Mode definitions
```

新增一个普通内容项时，核心代码不应出现大量新的 if/switch。

注意：不要为了抽象而抽象。只有存在两个以上真实同类实现时再提取公共接口。

## 2. 配置与行为分离

配置负责：
- 数值；
- 标签；
- 可调参数；
- 视觉参数；
- 内容声明。

行为模块负责：
- update；
- attack；
- movement；
- effect；
- validation；
- rendering。

禁止在配置对象中逐步塞入大量复杂匿名函数，导致配置重新变成不可维护的业务中心。

## 3. 游戏模式边界

建议统一定义模式生命周期：

```text
enter
start
update
draw
pause
resume
exit
destroy
```

普通塔防与 conquest 使用共同的 Game/runtime 能力，但独有的规则放在各自 mode 下。

目标：以后新增模式时不需要复制 `Game`。

## 4. 存档版本

如果当前使用 localStorage，建立：

```js
{
  version: 1,
  ...
}
```

并预留 migration：

```text
v1 → v2
v2 → v3
```

结构重构不得擅自清除已有用户存档。

验收必须覆盖旧存档读取。

## 5. Level 数据组织

关卡数据建议按模式/关卡拆分：

```text
js/data/levels/defense/
js/data/levels/conquest/
```

通过统一索引注册。

目标：
- 新关卡尽量只新增数据文件；
- LevelManager 不需要硬编码所有关卡；
- 单个关卡错误不影响全量结构。

## 6. Tower/Enemy 扩展

为实体明确最小接口，不做大型继承树。

优先组合：
- targeting strategy；
- attack behavior；
- status effect；
- rendering helper。

避免未来每加一种塔就在 `Tower.update()`、`Tower.draw()`、`UI` 和 `CONFIG` 四处追加巨大 switch。

## 7. UI 扩展

UI 使用 controller/component 职责边界。

新增弹窗/面板时：
- 自己拥有 DOM 查询；
- 自己拥有事件；
- 自己处理 destroy；
- 通过公开方法与 Game 交互；
- 不直接读写大量 Game 内部字段。

## 8. 调试能力

保留并完善 `?debug=1`。

建议未来调试面板只读取公开 runtime metrics：
- FPS；
- entity 数量；
- projectile 数量；
- particle 数量；
- object pool 使用；
- 当前 mode；
- 当前 level/wave。

调试代码不得污染正式玩法逻辑。

## 9. 架构决策记录

未来重大选择使用轻量 ADR：

```text
docs/architecture/decisions/
0001-keep-no-build-tool.md
0002-global-compatibility-layer.md
0003-native-es-modules-evaluation.md
```

每份记录：
- 背景；
- 决策；
- 原因；
- 代价；
- 可撤销条件。

## 10. 原生 ES Modules 评估（独立后续工单）

在所有核心大文件已经按职责拆分后，才评估：

```html
<script type="module" src="js/bootstrap/app.js"></script>
```

评估内容：
- 本地静态服务器兼容；
- 加载顺序；
- 全局 API；
- 测试脚本兼容；
- 浏览器目标；
- 是否能删除全局兼容层。

结论可以是“暂不迁移”。不要为了现代化而强制迁移。

## 11. 未来路线图建议

### R1：结构稳定
- 完成 600 行治理；
- dependency map；
- smoke tests；
- 文档分类。

### R2：内容扩展效率
- 配置/关卡 registry；
- 新 Tower/Enemy 接入流程；
- fusion 数据统一。

### R3：模式扩展
- defense/conquest mode 生命周期统一；
- progression/saves 边界稳定。

### R4：工程质量
- Playwright 主流程回归；
- 性能基准；
- debug metrics；
- 错误记录机制。

### R5：再评估模块系统
- 原生 ES Modules；
- 是否继续全局兼容层；
- 不改变“无构建工具”原则，除非未来需求明确变化。

## 验收标准

- [ ] 新增内容有明确接入点。
- [ ] Game 不需要持续吸收模式细节。
- [ ] UI 与 Game 不再高度互相读取内部状态。
- [ ] 关卡数据按模式组织。
- [ ] 存档有版本策略。
- [ ] debug 能力有明确边界。
- [ ] 重大架构决策有 ADR 记录方式。
- [ ] 是否采用 ES Modules 被作为独立决策，而不是夹带在重构中。
