# Phase 0 工单：结构审计与依赖基线

## 任务目标

在不修改任何游戏行为的前提下，得到当前主分支的真实结构基线，为后续拆分提供依据。

## 当前背景

项目已经有模块化雏形，但普通 `<script>` 加载、全局变量、超大文件和历史文档可能导致实际依赖与文档描述不一致。任何结构重构前必须先确认真实代码。

## 涉及范围

- `index.html`
- `css/**/*.css`
- `js/**/*.js`
- 根目录测试与工具脚本
- `package.json`
- `README.md`
- `AGENTS.md`
- `docs/architecture-runtime.md`
- 现有测试报告

本阶段原则上不修改业务代码。

## 实施步骤

### 1. 生成文件清单与行数表

统计：
- path
- 文件类型
- 行数
- 字节数
- 是否 >600 行
- 主要职责

重点标记 `index.html`、`style.css`、`config.js`、`game.js`、`tower.js`、`enemy.js`、`ui.js`、`conquestGame.js`、`levelsData.js`。

### 2. 提取脚本加载顺序

从 `index.html` 记录所有 `<script src>` 的真实顺序，并为每个脚本记录：
- 提供的全局符号；
- 依赖的全局符号；
- 是否允许延后加载；
- 是否有循环依赖。

生成 `docs/architecture/script-dependency-map.md`。

### 3. 建立核心对象责任表

至少包含：
- Game
- UI
- Tower / FusionTower
- Enemy
- FusionSystem
- LevelManager
- RuntimeIndexes
- InkRenderer
- conquest mode 相关对象

每个对象标注：
- 当前职责；
- 不应承担的职责；
- 未来目标目录。

### 4. 检查 HTML/CSS 耦合

识别：
- 内联 `<style>`；
- HTML 中的行内 style；
- JS 中直接写入的大段 style；
- 高频 DOM ID/class；
- UI 初始化依赖。

### 5. 检查数据/逻辑耦合

重点检查：
- `CONFIG` 是否混合数值、视觉和行为；
- levels 数据是否混在控制逻辑；
- tower 类型行为是否集中在巨大 switch/if；
- UI 是否直接操作 Game 内部状态；
- conquest 与普通塔防是否共享/复制逻辑。

### 6. 建立测试基线

执行现有：
```bash
node test-balance.js
node test-fusion-recipes.js
```

并启动静态服务进行基础 smoke test。

若 Playwright 已有可执行用例，同时记录其结果；若只有依赖尚无正式用例，不在本阶段擅自补大套测试。

### 7. 输出审计结果

新增：
```text
docs/architecture/current-structure.md
docs/architecture/script-dependency-map.md
docs/architecture/refactor-boundaries.md
docs/test-results/structure-refactor-baseline.md
```

## 风险与注意事项

- 历史质量审计中的行数可能已经过期，必须重新统计。
- 不要因为发现 bug 就在本工单顺手修复；另开 bug 工单。
- 不要移动文件，否则会污染基线。
- 不要改脚本加载顺序。
- 不要改变 CONFIG 结构。

## 验收标准

- [ ] 有完整当前目录树。
- [ ] 有全部代码文件当前行数。
- [ ] 所有 >600 行文件已标注。
- [ ] 有真实脚本加载顺序。
- [ ] 关键全局依赖已记录。
- [ ] 有 Game/UI/Tower/Enemy 等核心责任边界。
- [ ] 现有测试结果已保存。
- [ ] 本阶段无功能行为变化。
