# moshou 结构优化全面执行与 600 行治理工单

- 项目：`PEPETII/moshou`
- 执行分支：`refactor/structure-600-lines-20260916`
- 日期：2026-09-16
- 目标：在保持纯静态 HTML5 + Canvas + Classic JavaScript 运行方式和既有玩法行为的前提下，完成所有超 600 行代码文件的职责拆分，并为后续扩展建立稳定边界。

## 1. 本轮硬性验收目标

1. `index.html`、`css/**/*.css`、`js/**/*.js`、测试和工具代码文件均不超过 600 行。
2. 不通过压缩代码、删除必要注释、合并语句或截断功能规避行数限制。
3. 继续使用普通 `<script src>` 和静态资源，不引入 Vite、Webpack、TypeScript 或新的构建链。
4. 保留现有 DOM ID/class、存档 key、全局兼容名称、脚本运行顺序和游戏玩法。
5. 每个阶段独立验证；失败时只回滚当前阶段，不覆盖已通过阶段。
6. 计划、完成报告和架构文档必须与实际仓库状态一致，不能把未验证内容写成已完成。

## 3. 子代理编排

### Phase 0：基线与门禁（可并行）

| 子代理 | 职责 | 只读/写入边界 | 输出 |
|---|---|---|---|
| P0-A | 文件、行数、脚本顺序、测试基线 | 只读 | 结构和行为基线 |
| P0-B | HTML/CSS DOM、样式级联和移动端风险 | 只读 | Phase 1 拆分边界 |
| P0-C | JavaScript 类方法、全局符号和加载依赖 | 只读 | Phase 2 拆分顺序 |
| P0-D | 测试、工具、文档引用影响 | 只读 | Phase 3 迁移清单 |

P0-A～P0-D 可并行；P0-E 由主代理整合并确认门禁。仓库已有相关基线文档，本轮以当前源码复核结果为准。

### Phase 1：入口与 CSS（必须串行）

- P1-A：把 head 内资源加载器、移动端适配和 bottom 初始化迁出为 bootstrap 文件。
- P1-B：把内联 `<style>` 和 body 静态 DOM 迁出，保留 DOM ID/class 和节点顺序。
- P1-C：把 `css/style.css` 按原级联顺序拆成多个片段，`style.css` 保留兼容入口。
- P1-D：检查脚本标签和样式标签顺序，确认入口与每个资源均小于 600 行。

P1-A～P1-C 不能并行修改 `index.html`；P1-D 是合并门禁。

### Phase 2：JavaScript 核心拆分（严格串行）

依赖队列：

`P2-A config/data → P2-B Tower → P2-C Enemy → P2-D UI → P2-E Game → P2-F Conquest → P2-G 全仓行数复核`

每项职责：

- **P2-A 配置与数据**：拆分 `CONFIG` 领域和 `LEVELS_DATA` 注册块；保留 `CONFIG`、`THEMES`、`LEVELS_DATA` 全局兼容访问。
- **P2-B Tower**：保留 `Tower`/ `FusionTower` 构造和公开方法协议；分出攻击、效果、投射物、渲染和融合实现。
- **P2-C Enemy**：移动、路径阻挡、受伤/死亡、状态效果和绘制分开；不复制敌人核心。
- **P2-D UI**：按菜单、图鉴、输入拖拽、塔信息/弹窗、通知、征服界面拆分；保留事件监听追踪和销毁能力。
- **P2-E Game**：让 `Game` 保留生命周期/编排，分出塔操作、波次、流程和渲染。
- **P2-F Conquest**：只保留征服模式独有规则，复用既有实体/系统；分出融合、波次、渲染和流程。
- **P2-G**：扫描全部 HTML/CSS/JS/测试/工具文件，若任何文件仍超 600 行，回到对应子代理继续拆分。

为避免 classic script 的隐式依赖被并行写坏，P2 子任务不得同时改 `index.html` 或同一个原始 JS 文件。每个子任务完成后才进入下一项。

### Phase 3：测试、工具和文档治理（可分为只读并行，写入串行）

- P3-A：运行 Node 测试、静态语法检查和文件行数检查。
- P3-B：检查所有脚本路径、CSS 路径和 Markdown 相对链接。
- P3-C：更新架构文档、README 结构树、AGENTS 规则中的真实路径。
- P3-D：创建本轮完成报告和未解决问题清单。

P3-A/P3-B 可并行只读；P3-C/P3-D 必须在验证结果确定后串行写入。

### Phase 4：未来扩展架构准备（在全部拆分通过后）

- 保留兼容层，不做全量 ES Module 迁移。
- 明确新增炮塔、敌人、关卡和征服内容的注册点。
- 记录下一阶段可选的模块化迁移，不在本轮引入构建工具。
- 只有发现真实行为缺陷时才另开修复工单，不能把玩法变更混入结构重构。

## 4. 写入与回滚规则

- 每个 Phase 形成独立提交或可独立回滚的 commit。
- 同一路径不得被并行代理写入。
- 代码迁移完成后，旧文件只能保留轻量兼容入口；确认无引用后才允许删除。
- 如果浏览器环境不可用，必须保留 Node/静态检查结果，并明确浏览器 smoke 未验证，不得伪称通过。
- 不能因为行数限制删除测试、注释、错误处理或降级逻辑。
